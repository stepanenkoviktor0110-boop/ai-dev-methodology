# Quick Reference — Task Decomposition

1. Scope задач разных волн для одного файла: в бриф ранней задачи — "только X", в бриф поздней — "файл уже есть с функциями X, добавить Y"; параллельные task-creator'ы не общаются (Seen: 3)
2. Wave ordering: задачи внутри одной "named wave" с зависимостями A→B→C получают разные числа; проверять wave(B) > wave(A) для каждой пары зависимостей (Seen: 3)
3. Verify all cross-references after task generation: file paths через `test -e`, depends_on — подтверждать что зависимость реально создаёт нужный артефакт (Seen: 2)
4. Тест на стыке задач — добавить явно в spec/AC задачи-владельца: агент downstream не читает decisions.md предыдущих задач, notes недостаточно (Seen: 2)
5. Wave поля — числа, не метки: audit = N+1, final = N+2; строки "audit"/"final" не проходят frontmatter schema-validation (Seen: 2)
6. String-output assertions — ограничивай scope: извлечь нужную секцию (regex/split), затем проверять значение внутри неё, а не по всему документу (Seen: 2)
7. Задача создаёт no-op stubs "для следующих задач": в бриф каждой заполняющей задачи явно добавить шаг "замени no-op stub на реализацию" (Seen: 2)
8. AC для markdown-only фич: формулировать через наличие конкретных артефактов, а не смысловых описаний — делает AC автоматически проверяемыми (Seen: 1)
9. Задача в одной волне ссылается на результат другой задачи той же волны: заменить зависимость на чтение общего source of truth, сохранить параллельность (Seen: 1)
10. Задача на удаление фичи/константы/поля: перед ревью проверить dead variables, stale comments, duplicate tests — не тратить review-раунд на предсказуемые артефакты удаления (Seen: 1)
