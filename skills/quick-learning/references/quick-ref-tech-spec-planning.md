# Quick Reference — Tech Spec Planning

1. При интеграции с внешним API — перенести в спек ВСЕ коды ответа, формат данных и edge cases; перед включением response shapes из code-research — сделать live API call для проверки (Seen: 3)
2. Верифицировать values/methods против реальной документации — не принимать на веру память или architecture docs (Seen: 3)
3. Перед написанием файловых путей в tech-spec — верифицировать через ls/glob, не из памяти или architecture docs; docs описывают намерение, а не реальность файловой системы (Seen: 2)
4. Верифицируй целевые файлы перед описанием операции: когда spec описывает "удалить X из N файлов" — grep по каждому файлу перед фиксацией типа операции; файл без X требует add, не replace (Seen: 2)
5. Когда требования к формату/ограничениям поступают итеративно — согласовать полную структуру и ограничения до кода, не переписывать реализацию на каждое уточнение (Seen: 2)
6. При завершении секции Implementation Tasks — проверить overlap "Files to modify" внутри каждой волны для предотвращения merge-конфликтов при параллельном выполнении (Seen: 2)
7. При добавлении auth flow к импортированным данным — проверить credentials + isActive, чтобы не обнаружить missing auth на user verification (Seen: 1)
8. Когда внешний сервис возвращает неожиданный результат — провести эскалирующую диагностику: параметры → curl → перечитать docs; найти рабочий обходной путь через существующие API-параметры (Seen: 1)
9. Когда запрос данных из внешней системы вернул пусто — перечислить и проверить все каналы/endpoints, чтобы не пропустить данные в альтернативном канале (Seen: 1)
10. При старте комплексного проекта — включить server action timing в scope MVP для получения baseline метрик до оптимизаций (Seen: 1)
