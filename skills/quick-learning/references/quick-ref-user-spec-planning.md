# Quick Reference — User Spec Planning

1. Генерируй все шаги deliverable целиком — частичный deliverable заставляет пользователя ловить недостающие части. (Seen: 3)
2. Когда появляется новая роль в интервью — сразу строй матрицу роль × возможности и валидируй с пользователем.
3. Когда пользователь добавляет нетривиальную фичу в ходе интервью — задай вопрос о влиянии на скоуп до обновления спека.
4. Когда клиент вносит правки в approved user-spec — проводи мини-интервью только по изменённым пунктам, не перезапускай полный цикл.
5. Когда в спеке список с числовым атрибутом (цена, оценка) — явно уточни, кто/что задаёт значение, до написания AC.
6. Когда user-spec описывает мгновенные операции (клик → запись в БД) — явно добавляй AC для сетевой ошибки и отката до валидации.
7. Когда user-spec для фичи, завершающей существующий скетч/stub с реальными API — сканируй все реализации API и включай найденные баги в AC.
8. Когда пользователь описывает несколько взаимосвязанных фич — явно уточни порядок реализации ДО инициализации первой папки фичи.
9. Когда стейкхолдер подтверждает декомпозицию целиком — валидируй каждый элемент отдельно, чтобы избежать bundle-confirmation bias.
10. Когда пользователь описывает фичу знакомым термином — спроси «кто потребитель и зачем?» до технических деталей; когда импортирует внешний фреймворк — открой его entry-point и перечисли зависимости до фиксации AC.
