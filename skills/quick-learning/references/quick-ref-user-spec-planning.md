# Quick Reference — User Spec Planning

1. Генерируй все шаги deliverable целиком — серия промптов, roadmap, план сессий, деплой-инструкция выдаются сразу, не частями (Seen: 3)
2. Для distribution-инструкций конечному пользователю — перечислить prerequisites на чистом окружении до выбора метода доставки (Seen: 1)
3. При 3+ последовательно зависимых deliverables — первый активный, остальные как planned-stubs с видимым прогрессом (Seen: 1)
4. Если репо содержит skills/модули из разных доменов — перечислить все домены и получить is_in_scope по каждому до написания спека (Seen: 1)
5. При появлении новой роли в середине интервью — сразу строить матрицу role × capabilities и валидировать с пользователем (Seen: 1)
6. Если пользователь описывает несколько взаимосвязанных фич — явно уточнить порядок реализации ДО инициализации первого folder (Seen: 1)
7. При amendments к approved user-spec — фокус-мини-интервью только по изменённым точкам, не перезапускать полный цикл (Seen: 1)
8. При обновлении user-spec для уже реализованной фичи — запустить code-researcher для diff требований против существующего кода (Seen: 1)
9. Если фича генерирует список с числовым атрибутом (цена, рейтинг) — явно спросить кто/что задаёт значение (LLM/каталог/ручной ввод) до AC (Seen: 1)
10. Если spec описывает instant-save (click → DB) — явно добавить AC для network error и rollback до валидации (Seen: 1)
