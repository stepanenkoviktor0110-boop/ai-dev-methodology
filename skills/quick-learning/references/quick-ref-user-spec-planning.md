# Quick Reference — User Spec Planning

1. Генерировать все шаги deliverable целиком — когда deliverable состоит из нескольких шагов, генерировать ВСЕ шаги сразу; частичный deliverable заставляет пользователя запрашивать доработку (Seen: 3)
2. Нетривиальная фича mid-interview — задать scope-impact вопрос до обновления спека, не расширять v1 до архитектуры другого уровня (Seen: 2)
3. Новая роль mid-interview — немедленно составить матрицу "роль × возможности" и согласовать с пользователем (Seen: 2)
4. Spec описывает CRUD-форму для одной сущности, а workflow — action над группой — уточнить кардинальность ("один или несколько?") до реализации (Seen: 2)
5. UI-задача добавляет visible disabled-кнопки как placeholder — не добавлять пока будущая задача не подтверждена (Seen: 2)
6. User spec вырастает до 3+ последовательно зависимых deliverable — оставить первый active, остальные создать как planned stubs (Seen: 1)
7. Описательный блок с требованием не отражённым в AC — следовать только AC, зафиксировать разрыв decision-записью и обновить user-spec (Seen: 1)
8. Клиент присылает правки к approved user-spec — точечное мини-интервью только по изменённым пунктам, обновить spec напрямую (Seen: 1)
9. User-spec описывает instant-save операции (клик → запись в DB) — явно добавить AC для ошибки сети и rollback до валидации (Seen: 1)
10. User-spec для фичи завершающей существующий скетч/стаб — в code scanning прочитать реализации всех API и включить найденные баги в AC (Seen: 1)
