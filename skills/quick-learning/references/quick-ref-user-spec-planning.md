# Quick Reference — User Spec Planning

1. Генерируй все шаги deliverable целиком: когда deliverable состоит из нескольких шагов — генерировать ВСЕ шаги сразу; частичный deliverable заставляет пользователя запрашивать доработку (Seen: 3)
2. Когда user-spec описывает instant-save операции (click → write to DB) — явно добавить AC для network error и rollback перед валидацией (Seen: 1)
3. Когда появляется новая роль в середине интервью — немедленно построить матрицу role x capabilities и валидировать с пользователем (Seen: 1)
4. Когда пользователь описывает "разделить UI-область на X и Y" — уточнить выживают ли существующие элементы взаимодействия в новом layout (Seen: 1)
5. Когда spec описывает CRUD-форму для одной сущности но целевой workflow — действие над группой — уточнить cardinality ("один или много?") до имплементации (Seen: 1)
6. Когда пользователь отклоняет предложенное упрощение — спросить "что теряется при упрощении?" перед продолжением (Seen: 1)
7. Когда фича генерирует список с числовым атрибутом (цена, оценка) — явно спросить во время интервью кто/что устанавливает это значение (Seen: 1)
8. Когда клиент присылает правки к утверждённому user-spec — проводить только mini-interview по изменённым пунктам, не перезапускать полный цикл (Seen: 1)
9. Когда пользователь описывает несколько взаимосвязанных фич для реализации — явно уточнить порядок реализации ДО инициализации первой папки фичи (Seen: 1)
10. Когда user-spec описывает delete/cleanup в системе с pipeline-статусами — ограничить удаление terminal-статусами (enriched/done), не значениями полей (Seen: 1)
