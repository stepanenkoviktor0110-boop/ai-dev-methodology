# Quick Reference — User Spec Planning

1. Генерируй все шаги deliverable целиком — серия промптов, roadmap, план сессий, деплой-инструкция выдаются сразу, не частями (Seen: 3)
2. Ослабляя access-check ради одной операции — перечислить ВСЕ операции под тем же предикатом, добавить отдельные проверки закрытым, протестировать каждый закрытый путь (Seen: 1)
3. Спек требует поле, которое текущий инкремент ещё не может заполнить — сделать conditional-путь с no-op на пустом значении и протестировать И пустой (сейчас), И заполненный (позже) вход (Seen: 1)
4. Расширяя правило матчинга ради пропущенного случая — перечислить соседние входы, которые оно теперь тоже ловит, убедиться, что ни один не из другого bucket (Seen: 1)
5. Новый read/write в общий mutable-store на горячем пути — встроить per-case изоляцию в базовый fixture и прогнать ВЕСЬ сьют, не только новые кейсы (Seen: 1)
6. Адаптируя guard/dispatcher/switch из шаблона — перечислить все возможные входы/роли/кейсы; ветки не из шаблона получают явный handler или явный deny-default (Seen: 1)
7. «Конвертировать каждый X коллекции C в форму Y» — заранее перечислить не влезающие в Y элементы и объявить судьбу каждого; после — сверить count и имена (Seen: 1)
8. Структурированный вход + числовые AC из него — вывести все счётчики за один проход в scratchpad и вставить эти числа везде; не пере-прозировать независимо (Seen: 1)
9. Вторая задача повторно находит gap, уже помеченный out-of-scope — эскалировать в спек/Decision и завести follow-up, не лепить второй локальный workaround (Seen: 1)
10. Фича генерит список items с числовым атрибутом (цена, скор, рейтинг) — до написания AC спросить, кто/что задаёт это значение (Seen: 1)
