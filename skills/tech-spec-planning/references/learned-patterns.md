# Learned Patterns — Tech Spec Planning

> Loaded by audit agents and retrospective only. Orchestrator loads only Promoted Patterns (in SKILL.md).

- When adding auth flow to imported data -> verify credentials existence AND isActive flag in the integration spec.
- When an external service returns an unexpected result during research -> escalate diagnostics (parameters -> curl -> re-read docs) before declaring a blocker.
- When output format requirements arrive iteratively -> agree on complete output structure with a mockup before writing code.
- When an external system returns empty results, OR a primary/current-state view returns empty or implausibly sparse against a reasonable expectation -> enumerate all available channels/endpoints, and check whether the view was cleared by a periodic/lifecycle process by looking for the entity's change-history/audit/derived representation, before concluding data is absent. Stakeholder-facing variant: before telling a stakeholder an artifact/feature "doesn't exist" (especially when they recall creating it) -> treat firsthand recollection as strong counter-evidence, run a cheap whole-tree filename+content sweep before concluding absence, and report scoped "not found in X/Y/Z" rather than bare "doesn't exist" (absence-of-evidence as proof, empty-view finality) (triads #392, #458).
- When speccing a complex project with server-side actions -> include performance timing baseline in MVP scope.
- When diagnosing performance on a low-traffic server -> check default timeout/connection pool/cache limits before optimizing code.
- When planning file sync between two repo versions -> launch code-research to classify diff depth before writing scope.
- When a feature combines client-only storage with server-side automation -> verify data-access layer compatibility before architecture decisions.
- When spec narrows an interview criterion (A or B -> only A) -> record in Technical Decisions: decided NOT to include B, because...
- When adding a metric to a dashboard without explicit time horizon -> clarify with user: launch / daily / all-time, before writing spec.
- When proposing hosting/stack -> clarify deployment region and regulatory constraints BEFORE proposing solutions.
- When completing Implementation Tasks -> check Files-to-modify overlap within each wave to prevent merge conflicts.
- When a feature has user file uploads to disk -> describe protected-API delivery (not static) in Architecture, to prevent IDOR.
- When a feature reads methodology files via GitHub Contents API -> verify those files are committed in target repos BEFORE writing AC (.gitignore risk).
- When writing curl in AVP for authenticated endpoints -> include auth header AND a without-key -> 401 case, to avoid false QA pass.
- When config contains a whitelist/filter -> clarify at which pipeline stage it applies and move it before the resource-intensive operation.
- When asked to remove X from repository -> clarify: git untrack (git rm --cached + .gitignore) vs physical deletion.
- When needing provider configuration (DNS, settings) -> ask client first whether they have control-panel access.
- When a tech-spec decision narrows/defers a user-spec requirement -> check if it appears in user-spec AC BEFORE writing the Decision.
- When a user rejects a proposed architectural simplification -> ask 'what distinction is lost by the simplification?' before continuing, to surface the missing key abstraction before implementation (triad #137)
- When designing a system via a specific tool for another executor → verify that executor's toolset before fixing architecture, to avoid binding the architecture to the designer's tool rather than the executor's (triad #246)
- When a classifier field groups radically different entity types in one table → check whether all types share the same attribute set, to avoid merging entities with different structures into one table (triad #247)
- When an external naming claim (stakeholder names a tech component, external doc names positional attributes, spec names a code symbol) is about to enter the spec → verify it against ground truth (project docs / code / grep) before recording, to avoid name-mirage from external assertions (triads #267, #287, #307)
- When moving a task (script, module, pipeline) from one execution environment to another → enumerate all implicit environment dependencies (env vars, filesystem, network, runtime, auth model) before migrating; and when validating a portable artifact while it still sits in the environment that produced it (co-located files, running local server, inherited state) → verify it detached in a stand-in of the consumer's isolated environment, exercising it exactly as a recipient who gets only the artifact would, to avoid assuming that existence equals portability and authoring-environment affordance blindness (triads #268, #454)
- When assigning a value to a named configuration field → trace how the consuming system actually reads and uses that value, to avoid conflating the field label with the machine contract (triad #279)
- When writing concrete method call signatures in implementation hints for a task that uses an external dependency → check the actually installed package version before recording call signatures in hints, to avoid stale API guidance from training memory (triad #293)
- When configuring data output that feeds a separate system → derive output field names directly from the consumer's parsing code, not from spec prose or convention, to avoid producer-side naming assumptions where consumer uses different names (triad #300)
- When designing a background process with a pre-qualification gate and considering adding a time-based cancel → check if the pre-qualification gate already covers the failure case before adding a time limit, to avoid treating long-running inputs as stuck when scope check already excluded oversized inputs (triad #303)
- When the Architecture section describes placement of a new UI component → re-read the user-spec for explicit layout constraints before choosing placement, to avoid default-layout assumption that ignores an explicit prohibition from user-spec (triad #308)
- When bulk-creating via API artifacts of a platform that has runtime-dynamic UI behaviors (dynamic filters, template-binding, context-aware behaviors) → create ONE instance via API, run the full end-to-end user scenario, only then scale, to avoid API/UI semantic divergence where structural equivalence in API ≠ behavioral equivalence at runtime (triad #309)
- When writing a derivative planning artifact (user-spec from TZ, tech-spec from user-spec) whose upstream source contains explicit defaults for the same concept → before encoding each policy, grep the upstream source for the concept by name and reconcile with its explicit default, to avoid pre-recorded default erosion where a recent interview exchange silently overrides an explicit default already recorded in the source (triad #311)
- When introducing a new state or value that must be valid across multiple independent system boundaries (validators, guards, persistence, UI, external contracts) → enumerate every boundary that enforces or validates that value and update all of them before marking the change done, to avoid single-layer completion where one boundary still rejects or mishandles the new value (triad #326)
- When new code handles a value that pre-existing records may store in older or unnormalized format → include at least one fixture row in legacy format alongside the happy-path fixture, to avoid happy-path fixture assumption that only exercises the new format and hides regressions on existing data (triad #330)
- When a task spec instruction contradicts an established project reference (architecture doc, decisions log, prior approved spec) → treat the established reference as authoritative and flag the spec instruction as a hypothesis to verify with the user, not as a newer override; do not use recency as authority (triad #336)
- When a task description references a backlog item, prior spec, or decision artefact by identifier → open and read that artefact in full before drafting the plan or picking an approach, to avoid approach-before-reading where the chosen direction conflicts with constraints already recorded in the referenced artefact (triad #342)
- When investigating why two outputs from the same intent diverge → sample at the exact coordinate of divergence and walk the full production pipeline at that point, not just inspect computed properties of named or semantic elements, to avoid named-element bias where the cause sits in an unnamed layer between the named ones (triad #343)
- When a brief asks to "match exactly" or be "1:1" with an external reference → enumerate fidelity axes (content, behavior, structure, visual, layout, assets, data model) and confirm with the requester which axes apply before starting, to avoid fidelity-dimension conflation where producer and requester mean different subsets of "exact" (triad #344)
- When writing a whitelist/validator check using a parser's canonicalized view of untrusted input → enumerate which properties the parser silently elides (default values, case folding, percent-decoding, port-default stripping, Unicode form) and cross-check against the raw input on every elision that matters for the guard, to avoid canonical-form blindness where the parser already normalized away the attacker's intent (triad #353)
- When about to add a new element drawn from a system spec or schema and validated working artifacts of that system already exist → first enumerate what elements are present in existing validated artifacts; treat that set as the active subset of the spec; introduce new elements only when absent from all artifacts or when spec explicitly marks them as encouraged defaults, to avoid spec-over-example authority bias (triad #356)
- When validation framework offers a retrieval-test endpoint AND end-user surface is a separate cached pipeline → after each change always re-test on the user surface with forced cache reset, not only on the on-demand test surface, to avoid test-surface gap where "retrieval returns right snippet" ≠ "user gets correct answer" (triad retrieval-test)
- When replacing a static asset whose URL/path is stored as a literal string in persistent storage → keep original filename+extension, OR grep all storage for the old path and update atomically, to avoid broken references after asset replacement (triad #359)
- When inheriting a "dead code / unused artifact" verdict from a prior session's audit → search at least one additional reference channel (module/path string, dynamic imports, reflection, plugin/config discovery) before acting on the verdict, and apply same skepticism to own dead-code claims, to avoid single-lens reference search false-negatives (triad #363)
- When a new spec references a quantitative threshold (test count, coverage %, latency, error budget) borrowed from a closed/archived prior session's report → re-measure on the working branch, or rewrite the criterion as relative ("baseline + delta") that recomputes at execution time, to avoid archive-as-current bias where numbers from closed sessions guarantee pass or failure (triad #364)
- When an aggregation query expands two independent list-valued fields from the same record in one pass → expand each list in its own subquery/CTE, aggregate there, then join scalar results, to avoid multiple-expansion cross-product blindness where Cartesian product silently multiplies sums (triad #365)
- When writing an aggregation loop over an external data array → inspect one real sample for soft-delete/status flags before coding the loop; add guard conditions for each, to avoid implicit active-record assumption that inflates aggregates with voided/cancelled entries (triad #366)
- When a task description contains both illustrative pseudocode and executable tests that contradict each other → treat executable tests as the authoritative contract; use pseudocode only for intent, not as the implementation target, to avoid illustrative-code authority bias from proximity (triad #369)
- When refactoring a boundary node (server/host/owner) to push data via chain of pass-through wrappers to a deep leaf → enumerate the actual component chain by greping for each wrapper's direct children in code, then list every intermediate node as touched-file before assuming source→leaf reach, to avoid skipped-link drilling blindness (triad #371)
- When writing a test claiming to verify a derivation/transformation step inside a larger unit → invoke the unit and assert on its observable output; if expected value is recomputed locally for convenience, the assertion target must still be the unit's output, not the local recomputation, to avoid the re-derive-in-test fallacy where the test body re-runs the derivation by hand and never executes the unit under test (triad #372)
- When about to write a `file:line` (or `file:line-range`) citation inside a spec/decision/audit → the writing step itself opens the file at that exact offset and confirms the line carries the claim; if evidence sits a few lines away, cite that line instead, to avoid skim-cite line drift where a numeric pointer binds to a memorable nearby context line and lands on adjacent material that does not carry the claim (triad #374)
- When running a bulk operation driven by a discovery-tool list over a finite known scope (delete-all, audit-all, transform-all) → cross-check the returned count via an independent enumeration (different tool/command) before treating the list as exhaustive; reconcile any mismatch before acting, to avoid the discovery-tool exhaustiveness assumption. Specifically, when a list/query returns a row count equal to the endpoint default or page-limit → read equal-to-limit as truncation: paginate to exhaustion or tighten with a server-side filter before drawing any conclusion (especially a negative one), not just a generic count cross-check (triads #376, #411)
- When verifying a callback the framework invokes for you (event listener, hook, IRQ/webhook handler) → exercise it by triggering the real framework dispatch, never by hand-calling it with fabricated arguments, to avoid framework-contract bypass (triad #385)
- When a quantitative gate (completeness %, pass rate, error count) is computed by a command whose input set is narrower than the unit being judged → align the measurement's scope with the artifact under judgment before reading the number as a verdict, to avoid measurement-scope mismatch (triad #386)
- When a reviewer confidently asserts a specific verifiable fact is wrong and proposes a correction, OR a deliverable states any claim that is cheaply checkable against a live authoritative source yet also available from training/prior knowledge → run the cheapest direct live check that settles the fact before acting on it or presenting it as fact; assertiveness and training recall are not evidence — mark unverified content as hypothesis, to avoid confidence-transfer bias and training-prior-as-verified-fact (triads #387, #453)
- When changing behavior by flipping a high-level mode/environment selector while a narrower explicit override (env var, flag, connection string) is pinned → find which layer actually resolves the value and change it there, not just the mode selector, to avoid override-precedence blindness where the narrower override silently wins (triad #397)
- When about to reuse a previously self-authored condensed restatement of a canonical rule/spec/instruction in a new artifact → re-derive from the canonical source each time and treat prior compression as disposable, not authoritative, to avoid self-paraphrase meaning-drift (triad #400)
- When about to query a human/authority to clarify a task → first exhaust cheap available sources (docs, knowledge base, prior records); reserve human questions for gaps those sources don't close, to avoid premature-inquiry bias (triad #401)
- When asked to retrieve reference facts that live behind an authenticated/interactive surface (control panel, login, owner, support ticket) → first check whether the same facts are observable from a public/zero-auth source (registry, public lookup, DNS/whois, exposed metadata) and derive them there before requesting credentials or access, to avoid gated-source default (triad #437)
- When the convenient path to needed reference data is gated/failed while you hold an owned artifact containing the same data in a proprietary/binary/opaque format → attempt to decode the owned artifact (known container/codec) before declaring the task blocked or scoping it down, to avoid opaque-format-as-unusable (triad #404)
- When access to a remote endpoint degrades intermittently while both ends verify healthy, OR a remote host/service times out from your location and you're about to conclude it is down/broken → suspect the shared transport (ISP/route, DPI/filtering, tunnel/VPN, MTU), check provider known-issue notices, and get an independent external vantage (multi-node reachability probe / different network) before iterating endpoint-side fixes, asking the user to mutate endpoint state, or declaring the host down; if outsiders reach it, the fault is your local route, to locate the fault in the path not the endpoints (single-vantage global inference) (triads #405, #460)
- When computing a batch of relative values from one anchor (current date/time, baseline version, "current" state) while two sources disagree on the anchor → reconcile the anchor against the authoritative source before fanning out; verify the base once, not the derived results, to avoid tool-clock anchor trust (triad #407)
- When validating a fix to a non-deterministic system → treat the failure as probabilistic; sample many trials and report reduced-frequency/residual risk, not "eliminated", unless the mechanism guarantees it, to avoid small-sample determinism from K green runs (triad #409)
- When multiple distinct causes produce one identical observable symptom → obtain the single observation whose value differs across the hypotheses, not more evidence consistent with all of them, to avoid confirmation-gathering that never separates the candidates (triad #410)
- When a test mocks an upstream dependency to force a specific value and exercises a branch with it → verify the mocked return value is actually reachable from real inputs through the dependency before committing the test, to avoid phantom precondition testing of code paths that never occur in production (triad #419)
- When attaching a cross-cutting behavior (filter/guard/header-adder/interceptor) at a shared boundary to serve one subset of consumers → verify the boundary's real coverage; if it spans the whole surface, attach at a narrower sub-boundary covering only the intended subset and regression-check that other consumers are unchanged, to avoid shared-boundary scope blindness where a behavior added "for X" silently applies to all siblings (triad #426)
- When two layers each independently enforce the same constraint but produce different observable outcomes (one rejects, the other clamps-and-continues) → name the contract the spec actually requires, make exactly one layer the sole authority for it, and remove enforcement from the other rather than keeping both, to avoid redundant-gate authority blur where stacked validators silently disagree with no canonical layer (triad #427)
- When multiple independent processing layers (middleware, hook, filter, handler) handle the same unit-of-work → enumerate all reads across layers and deduplicate at the unit boundary, to avoid handler-isolation blindness where each layer looks self-contained locally and cross-layer fetch duplication is invisible (triad #434)
- When starting a task in a domain where hard-won constraints were already captured as persisted notes/memories (style rules, gotchas, "never do X"), OR writing new code in a category where a specific defect signature was already fixed once elsewhere in the same codebase → before producing, actively pull the persisted constraint-set and any prior in-codebase fix signatures and turn them into a pre-flight/self-review checklist applied in one pass, to avoid passive-memory bias and prior-fix non-propagation bias where known constraints resurface one-by-one as correction rounds (triads #443, #472)
- When an instruction states a blanket claim about existing project convention to justify skipping a quality step → enumerate the actual population the claim generalizes over and spot-check it before accepting the justification, to avoid premise-inherited-as-fact where a stated premise is trusted merely because it arrived embedded in the instruction (triad #450)
- When building a valid request/record for an opaque external system with uncertain field-mapping while a valid instance already exists there → fetch one existing valid instance via the read endpoint and copy its concrete field values, instead of inferring the mapping from owner labels/UI/URL/docs and firing guessed combinations at the write endpoint, to avoid guess-and-probe against an opaque validator (triad #451)
- When validating that a newly-added enforcement/isolation mechanism (permission gate, access control, RLS, sandbox) actually works → exercise the enforcement-critical cases with that mechanism ACTIVE in the same privilege/mode as production; a suite run under an elevated account or a config flag that globally bypasses the mechanism is no evidence, to avoid enforcement-inert validation (triad #455)
- When about to reuse/mirror an existing script/workflow/config as a proven template → confirm it has actually executed successfully at least once (run history/logs + its prerequisites/secrets exist), not just that it is present and looks complete, to avoid presence-implies-proven (triad #459)
- When a setting declared at a handler's/consumer's own definition site is assumed to also govern every caller/producer that logically depends on it → check whether the caller/producer path actually loads or evaluates that declaration, independent of the consumer path, to avoid config-locality blindspot (triad #463)
- When spinning up an isolated work environment (new branch/worktree/clone) from a canonical shared baseline ref → before trusting the copy, verify the baseline ref actually contains every input the work depends on and reconcile it to local state if not, to avoid remote-baseline completeness bias (triad #471)

- When launching task-creator agents → check the test runner (jest/vitest/pytest) and the test directories, and state both explicitly in every brief, so the generated TDD Anchor paths actually resolve.
- When setting depends_on for the audit wave → list EVERY task that produces an audited file, not only the last wave.
- When the question is about infrastructure, deploy or a production URL → read decisions.md (the changelog) BEFORE the project-knowledge docs.
- When a tech-spec Data Models section carries an UPDATE SQL for an existing table → have reality-checker diff that SQL against the real route handler, looking for existing parameters it dropped.
- When wave 1 creates a shared module with named exports and wave 2 consumes it → list EVERY exported symbol and pass the exact import line into each wave-2 brief, to avoid naming divergence.
- When planning an aggregation over a log table keyed on a column added by ALTER TABLE → check that historical rows are actually populated, not just that the column exists.
- When a task-creator brief carries a compatibility constraint (ES5/legacy) and the file already uses an HTTP pattern → name the permitted APIs with a sample line from the code, so an obsolete API is not picked.
- When transforming structured data (items, checklist, acceptance criteria) into prose (spec, report, Solution) → walk every source item and mark that it reached the target document.
- When a tech-spec contains a public POST endpoint with no authorization → apply the security checklist: CSRF/Origin, input sanitization, IP source, rate limit, security headers.
- When test-reviewer returns a fail on a tech-spec citing absent tests in files → treat it as a false fail; the prompt must say "review the plan, not the files".
- When a task touches three or more unfamiliar interfaces → verify each one before generating, to avoid O(N) errors.
- When planning a refactor from file structure or from a diagnosis → have code research confirm each artifact is actually used (rendered, imported), so the spec is not built on dead code.
- When assembling the list of decisions to discuss with the owner → filter by "does this change product behaviour?" — if not, decide it yourself.
- When the owner asks to check something against its original source → fetch the source first, then apply corrections.
