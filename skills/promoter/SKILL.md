# Promoter — Project Promotional Summary

Анализирует проект и генерирует промо-описания в 3 форматах.
Выход: один markdown-файл с секциями на двух языках.

## Step 0: Уточнение при запуске

Спросить у пользователя:

1. **Какие форматы нужны?** (по умолчанию — все три)
   - `client` — для заказчика
   - `portfolio` — для сайта/портфолио
   - `social` — для Telegram/соцсетей
2. **Какие языки?** (по умолчанию — оба: RU + EN)
3. **Есть ли исходное ТЗ?** — если да, запросить путь (нужно для формата `client`)

Если пользователь передал параметры в команде (например, `/promoter client ru`) — не переспрашивать.

## Step 1: Сбор информации о проекте

Прочитать (что доступно):

1. **CLAUDE.md** — описание проекта, стек, особенности
2. **Project knowledge** — `.claude/skills/project-knowledge/` если есть
3. **README.md** — если есть
4. **Манифест проекта** — `package.json`, `pyproject.toml`, `Cargo.toml`, `go.mod` (название, зависимости, стек)
5. **Структура папок** — `ls` верхнего уровня + `src/` для понимания архитектуры
6. **Объём кода** — подсчитать строки кода по типам файлов (без node_modules, .git, vendor, dist):
   ```bash
   find . -type f \( -name "*.py" -o -name "*.ts" -o -name "*.js" -o -name "*.tsx" -o -name "*.jsx" -o -name "*.go" -o -name "*.rs" \) -not -path "*/node_modules/*" -not -path "*/.git/*" -not -path "*/vendor/*" -not -path "*/dist/*" | xargs wc -l 2>/dev/null | tail -1
   ```
7. **Исходное ТЗ** — если пользователь указал путь, прочитать для извлечения терминологии клиента
8. **Git history** — `git log --oneline -20` для понимания этапов разработки

## Step 2: Анализ и извлечение

Из собранных данных извлечь:

| Поле | Описание |
|------|----------|
| **Что это** | Одно предложение: что делает система |
| **Для кого** | Целевой пользователь / бизнес |
| **Ключевые функции** | 3-5 главных возможностей |
| **Как работает** | Упрощённая механика (шаги / pipeline) |
| **В чём особенность** | Что отличает от типового решения |
| **Простота механики** | Почему это работает надёжно / просто |
| **Технический объём** | Строки кода, количество модулей, стек |
| **Терминология клиента** | Термины из исходного ТЗ (только для формата client) |

## Step 3: Генерация форматов

### Формат `client` — Для заказчика

**Цель:** отчёт, понятный человеку без технического бэкграунда.

Правила:
- Тезисный стиль — короткие пункты, не абзацы
- Ультра-простой язык, как будто объясняешь знакомому
- Технические термины — ТОЛЬКО те, что были в исходном ТЗ заказчика. Никаких новых
- Структура:
  ```
  ## Что было сделано
  (3-5 тезисов — что система делает, каждый на одну строку)

  ## Как это работает
  (Пошагово, 2-4 шага, максимально просто)

  ## Особенности
  (2-3 пункта — что выделяет, что было сложного и как решено)

  ## Объём работы
  (Количество модулей, строк кода, интеграций — в одном абзаце)
  ```

### Формат `portfolio` — Для сайта/портфолио

**Цель:** привлечь внимание потенциального клиента или работодателя.

Правила:
- На стыке детализации: достаточно подробно, чтобы понять что сделано, но не перегружено
- Простой язык, технические термины допустимы с пояснениями в скобках
- Описание основных функций — что система делает для пользователя
- Структура:
  ```
  ## {Название проекта}

  **Кратко:** {одно предложение — что это и для кого}

  ### Что делает
  (3-5 пунктов — ключевые функции с кратким пояснением каждой)

  ### Как устроено
  (Архитектура простым языком: из чего состоит, как части связаны)

  ### Стек и объём
  (Технологии, строки кода, модули — компактно)

  ### Результат
  (1-2 предложения — что получил заказчик / какую задачу решает)
  ```

### Формат `social` — Для Telegram / соцсетей

**Цель:** пост 500-700 знаков, понятный любому человеку.

Правила:
- НИКАКИХ технических терминов. Совсем. Не "парсер", а "программа, которая собирает данные". Не "API", а "подключение к сервису"
- Лёгкий, живой стиль. Как рассказ другу
- Структура поста:
  ```
  {Одно цепляющее предложение — что сделал}

  {2-3 предложения — как это работает простыми словами}

  {1 предложение — в чём фишка / почему это круто}

  {Опционально: 1 строка с цифрами — объём, скорость, автоматизация}
  ```
- Строго 500-700 знаков. Проверять длину перед выводом. Если не влезает — показать пользователю и спросить что сократить
- Эмодзи: допустимо не более 3 штук на весь пост, уместно и сдержанно
- Без хештегов (если пользователь не попросит)

## Step 4: Сборка документа

Собрать всё в один файл `work/promoter-output.md` (простой путь, без вложенности):

```markdown
# {Название проекта} — Promotional Summary

---

## Для заказчика (RU)
{содержимое формата client}

## For Client (EN)
{адаптация формата client для англоязычной аудитории — не дословный перевод, а переписанный текст с учётом культурных и стилистических отличий}

---

## Портфолио (RU)
{содержимое формата portfolio}

## Portfolio (EN)
{адаптация формата portfolio — стиль и акценты могут отличаться от RU-версии}

---

## Соцсети (RU)
{содержимое формата social}

## Social Media (EN)
{адаптация формата social — переписать, а не переводить; длина 500-700 символов сохраняется}
```

Включать только запрошенные форматы и языки.

## Step 5: Ревью с пользователем

Вывести результат и спросить:
- Что поправить?
- Тон подходит?
- Нужно добавить/убрать детали?

Применить правки → показать финальную версию.

## Антипаттерны

- НЕ использовать канцелярит ("данная система осуществляет...")
- НЕ использовать маркетинговый буллшит ("инновационное решение", "передовые технологии")
- НЕ преувеличивать объём или сложность
- НЕ добавлять функции, которых нет в проекте
- НЕ писать "мы", "я", "наша команда" — обезличено везде, во всех трёх форматах
- НЕ начинать с "Я разработал" / "Мы создали" (начать с того, что система делает)
